# 模型延迟与超时运行手册

本文记录模型超时的三层语义、37 题结构评测的耗时分布，以及一次真实 V3 导师流式回合的首字延迟。它用于容量和线上体验判断，不替代导师质量评测。

## 安全边界

`npm run --silent model:latency` 会调用当前配置的模型，但只使用仓库内固定的公开演示问题和演示学生数据。stdout 的最终脚本 JSON 只允许输出提交号、配置标签、端点哈希、数字指标和固定错误代码。启动时 stderr 会额外输出一条 `effective-model-config`，其中只允许出现经过校验和规范化的 base URL、安全来源及 shadowed 标记，详见 `runtime-configuration.md`。

禁止输出：

- API Key、Authorization、未校验端点、stderr 安全事件之外的端点原文或完整环境变量；
- 探针提示词、模型正文、流式 delta 内容或 provider output；
- service env、评测报告或数据库的绝对路径；
- 原始异常 message、stack、响应头或响应正文。

报告里的 `modelId` 是本地配置标签，不能单独证明中转 API 上游的真实模型身份。

## 三层超时

| 层级 | 在线默认值 | 评测默认值 | 语义 |
| --- | ---: | ---: | --- |
| 流式空闲超时 | 45,000ms | 120,000ms | 流式读取期间持续没有非空传输块才超时；每个非空原始块都会重置 |
| 模型总时长 | 120,000ms | 600,000ms | 单次模型请求的硬上限，不因流式活动重置 |
| 回合总时长 | 180,000ms | 900,000ms | 整个导师回合的硬上限，包含多次模型决策与工具执行 |

非流式请求不应用流式空闲超时，只受模型总时长和外层回合总时长约束。必须保持：`流式空闲 < 模型总时长 < 回合总时长`。

## 复现命令

在项目 worktree 根目录执行：

```powershell
npm run agent:eval -- --restart
npm run --silent model:latency
```

若 37 题评测因可恢复的模型服务错误中断，直接续跑，不能再次使用 `--restart`：

```powershell
npm run agent:eval
```

`model:latency` 使用与结构评测相同的 V3 导师入口、演示数据库、课程知识、模型适配器和评测超时档。它会读取最新结构评测报告并输出耗时分布。保留 `--silent` 可以阻止 npm 把脚本路径和更新通知混入证据输出。

## 指标定义

- `firstVisibleTextMs`：从导师回合开始，到 `onTextDelta` 第一次收到非空白文字。它对应学生界面最早可能显示文字的时间。
- `totalMs`：从导师回合开始，到完整 `runAgentTurn` 返回的时间。
- `visibleDeltaCount` / `visibleCharacterCount`：只记录数量，不记录任何正文。
- 37 题 `latencyMs`：单个评测案例的端到端耗时。一个案例可能包含 prelude、多次模型决策、工具和数据库操作，不能把它解释为单次模型请求耗时。
- 百分位采用 nearest-rank：`rank = ceil(percentile × count)`。
- 37 题 `totalMs` 是案例耗时之和，不含初始化、报告写入或服务冷却等待，因此不是整条命令的墙钟时间。

### 单次真实 V3 导师流式回合

#### 中转兼容修复前

- 测量时间：`2026-07-18T15:11:34.486Z`
- 首个可见文字：12,917ms
- 回合总时长：21,547ms
- 可见流：704 个 delta、1,072 个字符
- 最终模式：`DETERMINISTIC_FALLBACK`
- 模型错误：`MODEL_INVALID_RESPONSE`

这次调用证明模型能在约 12.9 秒开始持续输出，速度本身具备讨论线上使用的基础；但流式响应结束时没有通过客户端协议解析，整个回合最终降级。学生可能先看到模型流出的文字，随后得到降级结果，因此当前链路不能视为可上线。

补充诊断中的裸模型请求在收到响应头前被中转 API 以 `ECONNRESET` 断开；它与成功的 37 题正式导师请求不等价，不用于首字速度结论。正式 V3 导师探针能收到 704 个可见 delta，进一步把问题定位到兼容链路/响应收尾，而不是 50 秒超时或单纯网络丢包。

#### 中转兼容修复后

- 测量时间：`2026-07-18T17:23:36.517Z`
- 首个可见文字：12,706ms
- 回合总时长：30,273ms
- 可见流：735 个 delta、1,078 个字符
- 最终模式：`MODEL_ASSISTED`
- 模型、传输、协议错误：全部为空

这次探针返回 `status=SUCCEEDED`，证明真实 V3 导师回合已完整采用模型结果，不再降级。直接原因是中转 SSE 的线缆数据超过旧的 256KiB 共用上限；客户端现将 Responses 原始 SSE 线缆预算独立限制为 1MiB，同时继续保持最终正文 32,000 字符、单个 provider output 64KiB、provider output 总量 256KiB 等语义安全边界。

该次报告记录 `sourceCommit=bc45c2e496ba31330c04b375cbd3ba76b235f295` 且 `sourceTrackedTreeClean=false`，因为它用于提交前验证当前修复。报告未输出 API Key、端点原文、提示词、模型正文或原始尾包。

## 结果解读

- 修复后首字 12.7 秒、总时长 30.3 秒，并完整进入 `MODEL_ASSISTED`：流式链路已经可用，但首字等待仍偏长。
- 非流式结构评测 p50 27.9 秒、p95 70.4 秒、max 89.2 秒：若学生必须等完整回答才看到文字，体验偏慢。
- 修复前的 `MODEL_INVALID_RESPONSE` 已定位为 `BYTE_LIMIT` 并消除；模型、传输、协议错误码均为空。
- `gpt-5.6-sol` 已通过 37/37 结构评测，仍适合质量优先、允许等待的评测与判定场景。

已决策：线上导师和评测继续使用单模型 `gpt-5.6-sol`，不引入双模型。当前上线策略保留流式输出与三层超时，并用脱敏的传输/协议错误码持续监测中转兼容性。
