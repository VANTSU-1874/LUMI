# 证据私有存储与恢复

## 存储边界

`EVIDENCE_ROOT` 必须是仅由运行本服务的账户控制的独占目录。不要把它设为共享上传目录、软链接、junction、reparse point，也不要让它位于 `public/` 内或反向包含 `public/`。推荐保持默认的 `./data/evidence`，并限制其他账户的写权限。

服务会在建目录前后逐级检查祖先路径，在图片打开、重命名前后复验证据根目录与项目目录身份。路径身份发生变化时，上传会失败，且不会沿不安全路径清理文件。

## 启动恢复

正式启动必须先迁移数据库，再启动服务：

```text
pnpm db:migrate
pnpm start
```

数据库迁移不能省略，也不能依赖恢复命令代替。`prestart` 会在 `next start` 前自动执行 `pnpm evidence:recover`；恢复失败或等待恢复锁超时时命令返回非零，Next.js 不会启动。也可以在维护窗口单独执行：

```text
pnpm evidence:recover
```

恢复入口先用 Next 官方 `@next/env` 按生产优先级加载项目根目录中的 `.env.local`、`.env.production` 和 `.env`，然后才导入数据库与恢复服务。命令不会输出密钥内容。

恢复过程使用 SQLite 租约锁。同一时间只有一个进程处理超过宽限期的 PENDING 记录、严格 UUID 命名的过期孤儿文件和临时文件；持锁进程按租约三分之一的间隔续期。另一个并发进程会等待锁释放或过期，取得锁后自己完成一次幂等恢复，不会以“跳过成功”绕过启动门控。等待超时、续租失败或 owner 丢失都会让命令失败并阻止启动。只有 BUILD 项目可以在成功完成 PENDING 文件后进入 TROUBLESHOOT，TRANSFER 与 COMPLETE 等后续阶段不会倒退。

测试或特殊部署可配置 `EVIDENCE_RECOVERY_LEASE_MS`、`EVIDENCE_RECOVERY_WAIT_TIMEOUT_MS` 与 `EVIDENCE_RECOVERY_POLL_INTERVAL_MS`；默认启动会等待恢复完成。生产环境不要把等待超时设得短于正常恢复耗时。

## 故障处理

- 若提示路径不安全，检查 `EVIDENCE_ROOT` 的每一级祖先是否为链接或 junction，并检查它与 `public/` 的包含关系。
- 若恢复命令失败，不要绕过 `prestart`。先修复数据库迁移、目录权限或路径配置，再重新执行恢复命令。
- 不要手工删除数据库仍引用的 READY/PENDING 文件。恢复只处理创建时间与文件 mtime 都超过宽限期的 PENDING；只清理超过宽限期、严格 UUID 加安全图片扩展名且无数据库引用的最终孤儿文件，以及严格 `.UUID.tmp` 临时文件。未知文件会保留。

## 迁移兼容说明

项目尚未发布时直接修正了历史 `0005` 的证据复制表达式：真正的空字符串和全空格标签统一写为“历史证据”，其他标签截到 80 个字符。原因是旧表达式会让真正空标签在 `0005` 的长度约束处中断，后续迁移根本没有机会修复。正式迁移测试覆盖空字符串、空格、超长和多行标签；已经记录为应用完成的 `0005` 或 `0008` 不会重跑，只会继续执行 journal 中更新的后续迁移。
