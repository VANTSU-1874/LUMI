### S0 步骤

**A. 部署前体检（先看，不要改）**

- [ ] SSH 登录，记录 `free -h`（内存）、`df -h`（磁盘）、`node -v`
- [ ] **备份 Caddy 配置**：`cp /etc/caddy/Caddyfile /etc/caddy/Caddyfile.bak-$(date +%F)`
- [ ] 记录现有站点的域名与端口，确认 Lumi 用 3000 不冲突
- [ ] ⚠️ **内存检查**：`next build` 峰值需 2–3GB。若可用内存不足，**先加 swap**（`fallocate -l 4G /swapfile` → `mkswap` → `swapon`），或改为本地构建后上传产物。**不要在内存不足的机器上直接构建——会拖垮同机的现有站点。**

**B. 部署 Lumi（内部端口，先不暴露）**

- [ ] 拉代码、`pnpm install`、`pnpm build`、跑数据库迁移与种子
- [ ] 用 systemd 托管，监听 `127.0.0.1:3000`（只绑本地，不直接对公网）
- [ ] 本机 `curl http://127.0.0.1:3000` 确认应用起来了

**C. 接入 Caddy（关键：不要动现有站点的配置块）**

> ⚠️ **2026-07-19 更正**：S0 只读预检发现生产链路是 **Caddy → 3100 可信代理 → 3000 Next.js**。
> **Caddy 不能直接指向 3000**——绕过可信代理会缺少签名请求头，导致生产登录返回 403。
> 本节原先写的 `reverse_proxy 127.0.0.1:3000` 是错的，已更正为 3100。

- [ ] 在 Caddyfile **末尾追加**独立站点块，不修改任何既有块：
  ```
  chuyingai.cc.cd {
      reverse_proxy 127.0.0.1:3100
  }
  ```
- [ ] 确认可信代理（3100）已随应用一同启动，且它自己指向 3000
- [ ] `caddy validate --config /etc/caddy/Caddyfile` 校验后再 `systemctl reload caddy`（reload 不中断现有站点）
- [ ] ⚠️ **立即回归检查：现有站点是否仍正常访问。**异常就用备份回滚。

**D. Cloudflare 配置**

- [ ] Cloudflare 后台把 `chuyingai.cc.cd` 的 A 记录指向 `38.65.95.96`
- [ ] SSL/TLS 模式设为 **Full (strict)**
- [ ] 若 Caddy 自动签发证书受 Cloudflare 代理干扰：临时关闭橙云（DNS only）等签发成功再开启，或改用 Cloudflare Origin Certificate

**E. 验收**

- [ ] 公网访问 `https://chuyingai.cc.cd` 正常（不再是 530）
- [ ] 演示账号可登录，对话可跑通
- [ ] `pnpm qr:generate` 生成二维码，手机扫码可进
- [ ] **现有站点仍然正常**
- [ ] 部署耗时与踩坑点记入 `docs/runbooks/`

**验收**：拿到真实可访问的 URL 与二维码，现有站点无损，且知道重跑一次要多久。
